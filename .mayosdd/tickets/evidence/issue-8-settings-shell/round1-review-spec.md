- P1 (c) "First presentation appears near the centered palette position on the active display rather than the screen edge." `setFrameUsingName("SettingsWindow")` skips that placement whenever any frame is already saved; v0.3 used the same autosave name and AppKit writes it on close even if the user never moved the window, so upgrades and later opens restore a centered/old frame instead of the new geometry — the verified comment that this ordering keeps the computed first position from counting as a user-chosen frame is wrong.
- P2 (c) "First presentation appears near the centered palette position on the active display rather than the screen edge." Settings uses `PalettePlacement.activeScreen` (display under the pointer) while the live palette still anchors to `OpenRouter.primaryScreen`, so on a multi-display desk the first Settings frame is not near the actual centered palette.
- P3 (b) "The application owns one conventional menu bar with Settings at Command+, and standard Edit commands." The new Window menu (Minimize ⌘M, Zoom, Close ⌘W) was not asked for; those nil-targeted actions hit the key window, so with the palette key ⌘W/⌘M beep on a borderless non-closable panel and consume the keys.
